# Bushido Web UI

## 1. Purpose

Bushido Web is a minimal browser client for the Bushido/Citadel API.

It provides two primary capabilities:

1. Authenticate a Spartan.
2. Interact with Bushido through a command-line-style interface.

The frontend should feel like a small terminal or control console rather than a conventional dashboard.

The implementation should remain deliberately small. It is not intended to become a general-purpose frontend framework or administration interface.

---

## 2. Technology

Frontend:

- Elm
- HTML generated by Elm
- CSS
- Browser `fetch`/HTTP through Elm's HTTP facilities
- No React
- No JavaScript application logic unless required for Elm bootstrap
- No frontend component library

Backend:

- Citadel
- FastAPI
- REST/JSON
- Bearer-token authentication

Deployment target:

- Static frontend hosting
- Citadel remains independently deployed as an Azure Container App

---

## 3. Design

### Visual language

The UI uses a minimal cyberpunk / hacker-terminal aesthetic.

Characteristics:

- near-black background
- restrained green/cyan terminal accents
- monospace typography
- thin borders
- subtle terminal/grid elements
- high contrast
- minimal animation
- no gradients-heavy "gaming" aesthetic
- no large dashboard cards
- no unnecessary icons
- no decorative clutter

The interface should look like a functional terminal from a science-fiction system, not a conventional SaaS dashboard.

Example conceptual layout:

```text
┌─────────────────────────────────────────────────────────────┐
│ BUSHIDO // CITADEL                              ONLINE ●    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  SPARTAN: noe                                               │
│                                                             │
```

Desktop is the primary target, but the interface must remain usable on a phone.

## 4. Application states

The application has two main states:

```text
Unauthenticated
      │
      │ successful login/register
      ▼
Authenticated
      │
      │ logout / invalid authentication
      ▼
Unauthenticated
```

Elm should model these states explicitly rather than using loosely related Boolean flags.

Conceptually:

```elm
type AuthState
    = LoggedOut
    | Authenticating
    | LoggedIn Spartan
    | AuthFailed String
```
